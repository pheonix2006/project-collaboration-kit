# 标准项目跨会话合作机制

这是一套用 Git 管理的长期项目跨会话协作机制规范，帮助人和代理在新会话中以低上下文成本恢复正确的工作。

## 它解决什么问题

长期项目常把聊天记录、当前任务、已过期计划、设计结论和踩坑记录混在一起：新会话不知道先读什么，也很难判断哪一份材料仍然有效。本仓库定义信息职责、主要权威位置、材料生命周期，以及读取与写回的协作约定，让工作能够追溯而不会把历史误当成当前指令。

## 适用与不适用

适用于需要多次会话、多位协作者或多代理持续推进的软件、研究、实验和运营型项目，尤其是项目状态、计划和证据会持续累积的场景。

不适用于只需一次性沟通的极小任务，也不试图替代代码、测试、实际配置或运行产物本身的技术权威性。它提供协作机制，不规定业务架构、模型选择、运行命令或固定目录布局。

## 信息职责

| 职责 | 回答的问题 | 使用要点 |
| --- | --- | --- |
| 稳定规则与入口 | 长期规则是什么、某类问题去哪里找 | 保持短小稳定，不写单次任务细节。 |
| 项目总览 | 项目为何存在、服务谁、目标和非目标是什么 | 记录稳定边界与质量目标。 |
| 当前状态 | 现在在做什么、已验证到哪、下一步是什么 | 只保留一个项目级当前入口。 |
| 当前设计与当前计划 | 为什么这样构成；已确认且允许怎样执行、验收标准是什么 | 设计记录关键取舍，被替代后退出当前入口；计划记录已授权执行和验收条件，完成、取消或被替代后退出当前入口。 |
| 历史证据 | 做过什么、如何验证、产物在哪里 | 只用于追溯，不自动恢复执行。 |
| 可复用经验 | 哪些故障规律可跨任务复用 | 用“症状 / 原因 / 规避 / 证据”沉淀稳定规律。 |

这些是信息职责，不是六个必须照搬的目录。每一类事实应有一个主要权威位置，其余位置只做摘要和链接。

## 推荐阅读顺序

1. 阅读 [核心原则](docs/principles.md)，理解权威来源、状态和验证的基本边界。
2. 阅读 [信息权威来源](docs/source-of-truth.md)，确定六种职责如何各归其位。
3. 阅读 [文档生命周期](docs/document-lifecycle.md)，区分当前有效、可执行、完成、替代和历史材料。
4. 阅读 [跨会话工作流](docs/cross-session-workflow.md)，按需执行渐进读取、任务推进与里程碑写回。
5. 阅读 [项目定制指南](docs/customization-guide.md)，再决定本项目需要采用哪些职责和载体。
6. 需要真实演进背景时，阅读 [benchmark_eval 案例](docs/case-study/benchmark-eval.md)。

本规范的完整边界与设计依据见 [设计规格](docs/superpowers/specs/2026-07-22-project-collaboration-kit-design.md)。

## 在其他项目中选择性采用

先保留稳定规则与入口、项目总览和单一当前状态入口；当项目出现复杂决策时再增加当前设计与当前计划；只有需要追溯时才建立历史证据索引；确认可跨任务复用后才沉淀经验。每一类职责可由单文件、目录、Issue、知识库或运行产物索引承载，关键是明确主要权威位置和状态，而不是复制本仓库的文件名。

## 第一版明确不做

第一版只维护可解释的规范，不提供下游项目模板、侵入式管理目录、项目画像、命令行工具、初始化或检查脚本、结构定义、迁移工具、自动同步或集中保存其他项目状态的服务。这些能力是否值得建设，留待多项目复用后再评估。
