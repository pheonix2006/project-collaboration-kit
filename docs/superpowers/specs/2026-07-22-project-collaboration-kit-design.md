# 标准项目跨会话合作机制设计

日期：2026-07-22

状态：已批准，待实施

## 1. 定位

本仓库是一套用 Git 管理的“长期项目跨会话协作机制规范”。它负责说明一个项目应如何
组织当前状态、稳定设计、执行计划、历史证据和可复用经验，让新会话能够用较低的上下文
成本恢复工作，同时避免旧计划和历史结论污染当前判断。

第一版只提炼和解释机制，不提供模板、脚手架、安装器、CLI 或自动同步能力。

## 2. 要解决的问题

1. 新会话不知道应该先读什么，容易整库加载或依赖聊天历史。
2. 当前事实、执行计划、设计结论和历史证据混在一起，source of truth 不清楚。
3. 已完成或已过期材料仍然像当前指令一样存在，可能被错误恢复执行。
4. 单次事实、可复用经验和稳定项目边界重复记录，长期产生内容漂移。
5. 多代理协作时，探索、判断、验证和最终决策的职责边界不清楚。

## 3. 目标

- 定义一套简单、可解释的项目信息分层。
- 定义新会话的渐进读取顺序。
- 定义会话结束或里程碑完成时的写回规则。
- 定义当前材料、历史材料和归档材料的生命周期。
- 说明哪些内容属于通用原则，哪些必须由具体项目自行决定。
- 用 `benchmark_eval` 的实际演进说明这套机制从哪里来、解决了什么问题。
- 将规范提交到独立 Git 仓库并推送到私有远端，便于后续复用和演进。

## 4. 非目标

- 不提供可复制的项目模板。
- 不创建 `.collabkit/` 或其他侵入目标项目的管理目录。
- 不设计 Project Profile 或按项目类型自动生成内容。
- 不实现 CLI、初始化脚本、检查脚本、Schema、迁移或同步系统。
- 不强制目标项目使用完全相同的目录名。
- 不集中保存其他项目的状态或历史。
- 不把 `benchmark_eval` 的 adapter、runtime、judge、模型、凭据或运行命令变成通用规则。

## 5. 核心模型

机制将项目信息分为六种职责，而不是要求六种固定目录。

### 5.1 稳定规则与入口

回答“这个项目长期遵守什么规则”和“遇到某类问题应该去哪里找”。它应当短小稳定，
不记录单次任务细节。

### 5.2 项目总览

回答“项目为什么存在、服务谁、目标和非目标是什么、系统由哪些稳定部分组成、质量目标
是什么”。开发日志不能替代项目总览。

### 5.3 当前状态

回答“现在正在做什么、已经验证到哪一层、当前阻塞是什么、统一下一步是什么”。项目级
当前状态应只有一个入口，不累积多代历史快照。

### 5.4 当前设计与执行计划

设计回答“系统当前为什么这样构成”；计划回答“已经确认并允许怎样执行”。设计被替代、
计划完成或取消后必须退出当前入口，避免旧指令被重新执行。

### 5.5 历史证据

按里程碑保存做了什么、如何验证、产物在哪里以及剩余缺口。历史证据用于追溯，不直接
充当当前指令。

### 5.6 可复用经验

保存能够跨任务复用的故障模式，建议使用“症状 / 原因 / 规避 / 证据”。单次事故过程
属于历史证据，只有稳定经验才进入这一层。

## 6. Source of truth 原则

- 对话不是权威来源；会影响后续判断的结论必须写回项目仓库。
- 一类事实只指定一个主要权威位置，其他位置只做摘要和链接。
- 当前状态与历史证据分离。
- 稳定规则与单次执行细节分离。
- 已确认设计与待讨论想法分离。
- 已授权计划与历史 TODO 分离。
- 当前报告与旧口径报告分离。
- 代码、测试、实际配置和运行产物仍然是对应技术事实的更高层证据，文档不能覆盖它们。

## 7. 生命周期原则

材料至少区分以下语义：

- **当前有效**：可以指导现在的判断。
- **当前可执行**：已经确认并允许执行。
- **已完成**：保留结果和证据，不再作为待办。
- **已替代**：必须指向新的权威内容。
- **历史材料**：只用于追溯，不能自动恢复执行。

项目可以用目录位置、索引或显式状态表达生命周期。规范推荐优先选择读者无需打开正文
就能判断状态的方式，但不强制固定目录结构。

## 8. 跨会话读取协议

新会话遵循渐进加载：

1. 先读稳定规则与项目入口。
2. 需要整体判断时再读项目总览和当前状态。
3. 需要架构判断时只读相关的当前设计。
4. 需要执行已确认工作时只读对应的当前计划。
5. 需要追证时先通过索引、标题或关键词定位，再读取一份相关历史记录。
6. 只有明确需要追溯时才进入归档材料。

禁止默认整读全部开发日志、全部踩坑、全部设计、全部计划、全部报告或全部 archive。

## 9. 会话写回协议

在任务结束或达到里程碑时，根据事实职责选择写回位置：

- 当前目标、阻塞和下一步变化：更新当前状态。
- 长期边界或总体架构变化：更新项目总览或当前设计。
- 已确认且允许执行的复杂工作：形成当前计划。
- 本轮改动、验证和产物：形成里程碑记录。
- 可跨任务复用的故障规律：更新可复用经验。
- 计划完成、设计被替代或报告换口径：同一里程碑内完成归档和入口更新。

同一事实不应全文复制到多个位置。摘要必须链接主要证据。

## 10. 多代理协作原则

- 主代理负责目标边界、证据综合、方案取舍和最终决策。
- 子代理适合独立探索、跨目录检索、重复验证、日志整理和对照检查。
- 子代理结论不是最终事实；主代理应回读关键证据后再下结论。
- 验证结论必须说明验证层级，不能用一句“跑通了”覆盖静态检查、单测、集成、真实运行
  和业务质量之间的差异。

## 11. 项目定制边界

其他项目复用这套机制时，应根据自身规模决定：

- 使用哪些信息职责。
- 每种职责用单文件、目录还是外部系统承载。
- 哪些设计需要单独文档，哪些由代码和测试直接表达。
- 状态更新频率、归档粒度和验证层级。
- 是否需要报告、ADR、研究证据或运行产物索引。

复用的是问题分层、source of truth、生命周期和跨会话协议，不是复制
`benchmark_eval` 的目录或业务术语。

## 12. 第一版仓库内容

```text
README.md
AGENTS.md
docs/
  principles.md
  source-of-truth.md
  document-lifecycle.md
  cross-session-workflow.md
  customization-guide.md
  case-study/
    benchmark-eval.md
  superpowers/
    specs/
      2026-07-22-project-collaboration-kit-design.md
```

- `README.md`：仓库定位、推荐阅读顺序和适用边界。
- `AGENTS.md`：本仓库自身的协作规则，不作为下游模板。
- `principles.md`：核心原则和反模式。
- `source-of-truth.md`：信息职责和主要权威来源。
- `document-lifecycle.md`：当前、可执行、完成、替代和历史材料的流转。
- `cross-session-workflow.md`：新会话读取、任务执行和里程碑写回流程。
- `customization-guide.md`：其他项目如何按规模和类型取舍。
- `case-study/benchmark-eval.md`：从真实项目抽象机制的案例，不携带业务配置。

## 13. 验收标准

第一版完成时应满足：

1. 读者只看 README 就能理解仓库解决什么问题、何时适用和推荐阅读顺序。
2. 每类信息有清晰职责，不要求固定模板或目录。
3. 当前事实、历史证据、稳定经验和已授权计划之间没有职责冲突。
4. 跨会话读取与写回流程足够具体，可以由人或代理执行。
5. 定制指南至少覆盖小型项目、长期软件项目和研究/实验项目的取舍。
6. benchmark 案例明确区分通用机制和项目特定实现。
7. 文档相对链接有效，`git diff --check` 通过。
8. 仓库提交到 Git，并推送到当前 GitHub 账号下的私有远端。

## 14. 以后再决定的事项

只有经过多个项目实际复用并确认稳定后，才评估：

- 是否提炼模板。
- 是否增加结构检查脚本。
- 是否需要初始化工具。
- 是否需要自动同步或迁移。
- 是否按项目类型形成可选扩展。

这些能力不属于第一版，也不应提前预留侵入式目录或配置格式。
