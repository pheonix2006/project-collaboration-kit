# 项目定制指南

本机制复用的是信息职责、唯一权威来源、生命周期和跨会话协议，不是某个项目的目录树。先解决已经造成协作成本的真实痛点，再增加文档类型；例如没有持续的架构取舍，就不必先建立独立设计库。

## 定制方法

先回答四个问题：新会话最常缺什么信息？哪些结论会被旧材料误导？什么验证结果必须可追溯？哪些内容已由代码、Issue、知识库或运行平台可靠承载？然后为每类事实选择一个主要入口，并决定使用单文件、目录、Issue、外部知识库或产物索引承载。

“保留”表示职责需要明确且有唯一权威来源；“可合并”表示可由同一入口承载，但必须分节或标注状态；“可省略”表示当前没有稳定需求时不另建材料。省略文档类型不等于省略事实：事实仍应写到其选择的主要入口。

## 小型短期项目

适用于目标清楚、周期短、参与者少、变更和追溯需求有限的项目。

| 项目职责 | 最小采用建议 |
| --- | --- |
| 保留 | 简短稳定规则/入口；一个当前状态（可含目标、下一步和验证）；代码、测试、配置和产物作为技术事实。 |
| 可合并 | 项目总览可与稳定入口合并；简单计划可作为当前状态中的当前可执行区；里程碑证据可写入变更记录或任务/PR 的验收区。 |
| 可省略 | 独立当前设计、专门经验库、独立当前报告和复杂归档；除非任务出现架构取舍、反复故障或需对外汇报。 |

结束时至少更新当前状态或把任务标为已完成，并留下可定位的验证证据。不要为了“完整”复制长期软件项目的目录，也不要把一次性笔记误当长期规范。

## 长期软件项目

适用于持续迭代、多人协作、多组件、存在架构取舍或需要稳定交接的软件项目。

| 项目职责 | 最小采用建议 |
| --- | --- |
| 保留 | 稳定规则与入口、项目总览、唯一当前状态、当前设计、当前可执行计划、按里程碑的证据、可复用经验，以及代码/测试/配置/运行产物。 |
| 可合并 | 小型设计决定可并入设计索引或 ADR；当前报告可由当前状态和里程碑摘要承载；相近里程碑可共用一个有清晰索引的证据区。 |
| 可省略 | 没有实际读者或决策用途的日报、周报、重复 dashboard 和逐项操作日志；不必为每个模块建立独立文档。 |

重点是让当前设计与当前计划只保留仍有效、仍可执行的内容；已完成、已替代材料应退出默认读取路径。验证应按静态、单元、集成、真实运行和业务质量分层，而不是只记录“通过”。

## 研究/实验项目

适用于问题不断收敛、假设可能被推翻、实验条件和证据链比固定实现更重要的项目。

| 项目职责 | 最小采用建议 |
| --- | --- |
| 保留 | 稳定研究问题/入口、当前研究状态、当前有效假设或研究设计、已授权实验计划、实验与数据证据、可复用方法经验，以及可定位的数据/脚本/环境产物。 |
| 可合并 | 项目总览可与研究问题和范围声明合并；当前报告可和当前状态合并；小型实验计划可与对应研究设计共存，但必须明确当前可执行与草拟的边界。 |
| 可省略 | 在研究尚未稳定前的正式架构文档、过早的通用经验库、为每次探索单设的长期报告；原始实验日志也不应替代当前结论。 |

每次实验至少记录问题或假设、条件、产物位置、验证层级、结论与缺口。被推翻的假设应保留为历史证据并指向当前有效结论，不能因曾经“通过”就恢复为当前判断。

## 何时增加职责或材料

只有出现以下真实痛点时才新增或拆分材料：

- 新会话反复找不到当前目标、阻塞或下一步：建立或收紧唯一当前状态入口。
- 旧计划、旧报告或聊天记录反复被误执行：明确生命周期、索引和归档规则。
- 架构理由在任务间漂移：分出当前设计与当前可执行计划。
- 验证结论不可复查或同类故障反复发生：增加里程碑证据或可复用经验。
- 不同受众需要不同口径：新增当前报告，但仍链接其主要事实来源。

目录名、文档数量和外部载体都可变。尤其不要复制 `benchmark_eval` 的目录、运行配置、业务术语或历史材料；只根据本项目的痛点选择最小职责集合，并在增长后再迭代。
