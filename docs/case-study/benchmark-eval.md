# benchmark_eval 案例：从文档堆积到按职责恢复上下文

本案例说明一套长期评测项目的文档机制如何逐步形成。它只抽取协作问题和判断方法，
不把该项目的运行配置、业务对象或目录布局当作通用规范。若要直接采用本案例中的做法，
应先按[项目定制指南](../customization-guide.md)判断自身规模和痛点。

## 原始症状

项目持续跨会话推进后，入口文档同时承担长期规则、当前进度、运行说明和历史结论。新会话
为了判断现状，往往要读很长的入口或递归检索大量文档；检索还可能进入外部资产，迅速
占满上下文。

与此同时，状态、开发记录、问题记录、计划和报告都可能重复描述同一事实。某次结果已经
变化，另一份摘要仍保留旧口径；完成的计划和旧交接材料继续停留在默认读取路径，看起来
仍像待执行事项。顶层仓库的状态也不能代表嵌套资产的实际状态，单看一处容易遗漏证据或
发布边界。

这些症状不是“文档数量太少”，而是文档职责、当前性和读取路由不清楚。

## 演进前的问题

1. **入口既是规则又是日志**：稳定边界不断被一次性进度挤长，后续会话无法快速确定先读
   什么。
2. **当前事实与历史过程混写**：旧结论、旧待办和现行状态同时出现，读者必须靠正文语气
   猜测有效性。
3. **设计与计划相互代替**：架构理由、待讨论想法和执行清单没有清晰授权边界。
4. **证据与经验重复**：单次事故既写入开发记录又写入问题库，偶发现象容易被误当成稳定
   规律。
5. **验证口径被压平**：局部检查、集成链路、真实运行和输出质量可能都被概括为“已通过”，
   无法判断结论实际覆盖到哪一层。
6. **归档只移动文件，不更新入口**：材料虽然被保存，默认路由仍可能指向旧内容；反过来，
   被忽略的归档文件也可能根本没有进入版本控制。

## 形成的通用机制

演进后的做法不是增加一套统一模板，而是把信息分配给清楚的职责，并让默认读取链只指向
当前有效内容：

| 信息职责 | 在案例中的作用 |
| --- | --- |
| 稳定规则与入口 | 保留长期边界、阅读顺序和文档地图，不再承载单次运行细节。 |
| 项目总览 | 说明项目目标、稳定组成和不应跨越的集成边界。 |
| 当前状态 | 只设一个项目级入口，汇总当前目标、验证层级、阻塞和统一下一步。 |
| 当前设计与当前计划 | 当前设计保存已经确认且仍有效的关键取舍，被替代后退出当前入口；当前计划只保存已经确认并允许执行的复杂工作，完成或取消后退出当前入口。 |
| 历史证据 | 按里程碑记录改动、验证、产物和缺口，并通过索引按需追溯。 |
| 可复用经验 | 只收录获得稳定证据支持的故障模式，按“症状 / 原因 / 规避 / 证据”组织。 |

项目进一步用目录位置和索引表达材料生命周期：当前设计和当前计划位于默认入口可达的位置，
已完成、已替代和旧口径材料转入历史路径；当前报告与旧报告分层路由。新会话先读稳定规则
与入口，只有任务需要时才进入项目总览、当前状态、相关当前设计或当前计划，追证时再通过
索引打开一份相关历史证据。

验证也被明确分层。局部规则检查只能支持局部结论，组件共同工作属于集成验证，真实环境
链路和输出是否达到业务目标还需分别报告。这使“基础设施可运行”和“任务质量达标”不会
互相替代。

## 仍然存在的局限

- 机制依赖维护纪律。当前状态若长期不更新，单一入口只会形成单一的过期来源。
- 目录和索引能表达状态，但不能自动证明正文、代码和实际运行仍然一致；技术结论仍需回到
  代码、测试、配置和可定位产物核对。
- 归档降低默认上下文成本，也增加了维护链接、索引和版本控制状态的责任。
- “可复用”需要多次证据或清楚的机制依据。只改变存放位置，不能把单次事故自动升级为
  通用经验。
- 多代理可以加速检索和重复验证，但关键证据仍需主代理回读；分工本身不产生权威结论。

## 不能泛化的内容

案例项目包含特定的评测对象、运行边界、外部资产、报告口径和嵌套版本库关系。这些内容
决定了它自己的仓库地图、风险检查和发布顺序，但不是所有软件或研究项目都需要的职责。

同样不能直接泛化的还有：具体目录名、报告数量、归档粒度、状态更新频率、验证命令以及
某类运行产物是否进入版本控制。其他项目应复用问题分层与判断标准，不应复制案例项目的
业务术语和文件树。

## 其他项目可复用的判断方法

采用机制前，可以依次回答以下问题：

1. 新会话最容易缺失的是稳定边界、整体背景、当前状态，还是某次历史证据？先修复最短
   读取链，而不是先建完整目录。
2. 哪类事实在多个位置重复？为它指定一个主要权威位置，其他位置改为摘要和链接。
3. 读者能否在打开正文前判断材料是当前有效、当前可执行、已完成、已替代还是仅供追溯？
4. 当前设计是否只解释取舍，当前计划是否确实获得执行授权？如果答案是否定的，先分开
   讨论、判断与执行。
5. 历史证据是否记录了范围、验证层级、结果和缺口？可复用经验是否有超出单次事故的证据？
6. 默认读取是否会进入完整日志、全部归档或外部资产？若会，先增加索引和停止条件。
7. 文档结论是否能回到代码、测试、配置或运行产物核对？无法核对时，应标记未知，而不是
   用旧摘要补全。
